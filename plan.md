# TNPSC Book RAG — MVP Implementation Roadmap

## 1. Purpose

Build an English-only RAG backend for Tamil Nadu State Board textbooks for standards 6 through 10. The system must extract structured content from digital PDFs, preserve page and image provenance, provide standalone semantic search, and optionally generate LLM explanations from retrieved textbook evidence.

The implementation order is deliberately evidence-first:

1. Establish the storage and data foundations.
2. Extract trustworthy, page-linked content.
3. Prove retrieval quality without an LLM.
4. Assemble deterministic, inspectable context.
5. Add grounded and supplemented LLM answers.
6. Harden the complete MVP.

An LLM must not compensate for weak extraction or retrieval. Each phase has an exit gate that must pass before the next phase begins.

## 2. MVP Scope

### Included

- English-medium textbooks only.
- Standards 6 through 10.
- Digital PDFs with an accessible text layer.
- Book metadata: title, standard, subject, edition/academic year, publisher, and language.
- Original PDF preservation.
- Page-level text and provenance.
- Printed page label and PDF page index as separate fields.
- Extraction and preservation of figures, maps, diagrams, photographs, and captions.
- Structure-aware, page-aware chunking.
- Local English embedding generation.
- PostgreSQL with pgvector.
- A semantic-search API that does not require an LLM.
- An LLM answer API with two modes:
  - `textbook_only`
  - `textbook_plus_general`
- Optional SSE answer streaming with a final validated structured answer.
- Free hosted LLM providers accessed through PydanticAI v2.
- Typed and validated answer outputs.
- Structured JSON logging and OpenTelemetry instrumentation.
- Ruff, `ty`, Pyrefly, pytest, and retrieval/answer evaluation gates.
- Docker-based local development.

### Explicitly deferred

- Tamil extraction, search, or answer generation.
- Scanned-PDF OCR.
- Visual question answering or multimodal embeddings.
- Automatic description of uncaptioned images.
- Hybrid lexical/vector retrieval.
- Reranking models.
- User accounts, subscriptions, payments, and multi-tenant authorization.
- Frontend implementation.
- Distributed workers, Redis, Kubernetes, or production autoscaling.
- A separate LiteLLM proxy or other shared model gateway.
- Fine-tuning embedding or generation models.

## 3. Guiding Decisions

### 3.1 Extraction is the source of truth

- The original PDF is immutable source material.
- Docling output is preserved as a versioned extraction artifact.
- Derived pages, chunks, assets, and embeddings can be recreated.
- Raw extracted text and normalized retrieval text are stored separately.
- No OCR is forced for the MVP. A document without a usable text layer fails validation with a clear reason.

### 3.2 Provenance is mandatory

- Every searchable chunk must resolve to a document, book, and source page.
- PDF page index and printed page label must never be conflated.
- Bounding boxes are preserved when Docling supplies them.
- LLM citations are generated from backend evidence records, not free-form page numbers produced by the model.

### 3.3 Search remains local and independent

- Document and query embeddings are generated locally.
- Semantic search continues to work if all hosted LLM providers are unavailable.
- Retrieval scores are ranking signals, not confidence probabilities.

### 3.4 Free LLM providers are replaceable dependencies

- PydanticAI v2 provides the typed generation interface and provider fallback behavior.
- Provider names, model names, and fallback order are configuration, not business logic.
- The application must tolerate rate limits, model removal, provider outages, and changed quotas.
- No provider key is stored in the database or committed to source control.
- Only one routing/retry layer is used in the MVP; LiteLLM is not stacked beneath PydanticAI.

### 3.5 Laptop-aware operation

- Default ingestion concurrency is one document.
- Temporary files are removed after a successful ingestion.
- Page preview images are not generated by default.
- Only extracted document images are preserved.
- Local LLM inference is not part of the MVP.

## 4. Target Architecture

### Runtime components

1. **FastAPI application**
   - Book and document management endpoints.
   - Ingestion status endpoints.
   - Semantic-search endpoint.
   - Answer-generation endpoint.
   - Local query embedding.
   - PydanticAI v2 generation and structured-output validation.

2. **Ingestion worker**
   - Claims persistent jobs from PostgreSQL.
   - Runs Docling extraction.
   - Writes pages, assets, and chunks.
   - Generates embeddings in batches.
   - Performs cleanup and updates ingestion state.

3. **PostgreSQL with pgvector**
   - Catalog and document versions.
   - Ingestion state.
   - Page/chunk/image provenance.
   - Embeddings and semantic retrieval.
   - Retrieval and generation audit records.

4. **Shared artifact storage**
   - Local Docker volume for the MVP.
   - Original PDFs, Docling JSON, and extracted images.
   - Accessed through a storage abstraction so MinIO/S3 can be added later.

### Backend package and dependency boundaries

The backend contains two internal Python packages in one distribution and one `uv` project:

- `tnpsc_book_rag` is the application shell. It owns FastAPI, worker startup, settings,
  persistence, provider configuration, observability, and infrastructure adapters.
- `tnpsc_rag` is the domain-specific RAG core. It owns provider-neutral search, evidence,
  context, answer, and citation contracts plus orchestration policies.

`tnpsc_rag` is internal to this backend, not a separately published or generic RAG framework.
It retains TNPSC textbook concepts such as standard, subject, book/document identity, page
provenance, answer mode, and evidence citations.

Dependency direction is one-way:

`FastAPI/worker -> application services and adapters -> tnpsc_rag contracts`

The core must not import FastAPI, SQLAlchemy, pgvector clients, PydanticAI, or provider SDKs.
Instead, it defines small protocols implemented by infrastructure adapters. The standalone
search path uses retrieval only; the answer path composes retrieval, context assembly, and
generation without making search depend on an LLM provider.

### Initial deployment boundary

- One Compose project.
- One API container.
- One worker container.
- One PostgreSQL container with pgvector.
- One shared artifact volume.
- No Redis, LiteLLM proxy, or separate model-gateway container initially.

## 5. Data Model

The exact SQL is defined during implementation, but the following ownership boundaries should remain stable.

### `books`

Represents a conceptual textbook.

- Stable ID.
- Title.
- Standard: 6–10.
- Subject.
- Language: English for the MVP.
- Publisher.
- Optional board/catalog identifier.
- Created and updated timestamps.

The repository projects document count, active document, latest document/state, and derived catalog
status for the public Book resource. These availability fields are not independently mutable book
attributes and must remain consistent with document activation.

### `book_documents`

Represents a particular PDF/edition of a book.

- Book ID.
- Edition or academic year.
- Source filename and media type.
- Artifact location.
- SHA-256 checksum.
- File size and page count.
- Extraction/activation state.
- Active-version flag or activation timestamp.
- Created and updated timestamps.

A replacement edition creates a new document row. Existing citations remain tied to the edition from which they were produced.

### `pages`

- Document ID.
- Zero-based PDF page index, exposed with an explicit human-facing fallback label in the API.
- Printed page label, nullable and manually correctable.
- Width and height.
- Raw extracted page text.
- Normalized page text.
- Extraction warnings.

The API should expose an unambiguous human-facing page number while retaining the underlying PDF index.

### `assets`

- Page ID.
- Asset type: image, diagram, map, photograph, figure, or unknown.
- Artifact location.
- MIME type.
- SHA-256 checksum.
- Intrinsic pixel width and height when the preserved asset has a raster size.
- Caption, when present.
- Alt text, alt-text source, and decorative/informative status for explicit accessibility handling.
- Bounding box and coordinate origin.
- Optional canonical thumbnail artifact location plus intrinsic thumbnail dimensions.
- Docling reference/provenance metadata.

Binary image data is never stored directly in PostgreSQL.

### `chunks`

- Page ID.
- Document ID for efficient filtering.
- Stable sequence number within the document.
- Display text.
- Embedding text with book/chapter/section context.
- Chapter and section path.
- Content type: prose, heading, table, caption, or mixed.
- Token count.
- Content checksum.
- Source bounding boxes or provenance payload.
- Previous/next chunk relationship derivable from sequence.

Chunks should ordinarily remain within one page. Exceptional cross-page content must use an explicit page-link table rather than hiding the additional provenance.

### `chunk_pages`

Created if cross-page chunks are permitted.

- Chunk ID.
- Page ID.
- Span order.
- Optional character span.

### `chunk_embeddings`

- Chunk ID.
- Embedding model identifier and revision.
- Vector dimension.
- Content checksum used to create the embedding.
- Vector value.
- Created timestamp.

Only one active embedding model is required for the MVP. Keeping embeddings separate from chunks makes re-embedding auditable and avoids rewriting extracted content.

### `ingestion_runs`

- Document ID.
- Status and current stage.
- Worker identity.
- Docling version and configuration fingerprint.
- Chunker version and configuration fingerprint.
- Embedding model version.
- Started/completed timestamps.
- Retry count.
- Structured warning/error details.

### `answer_runs`

- Query text.
- Answer mode.
- Retrieval parameters.
- Retrieved chunk IDs and scores, preferably through a child table.
- Provider and actual model used.
- Prompt version.
- Token usage and latency when available.
- Generation status/error category.
- Validated structured answer or sanitized public problem for recovery.
- Request ID plus created/completed timestamps and retention expiry.

Do not store secrets or full provider credentials in audit records.

## 6. Lifecycle and State Machines

### Document lifecycle

`uploaded -> queued -> extracting -> chunking -> embedding -> ready`

Failure at any processing step moves the document to `failed` with the last successful stage and an actionable error. Retry creates or resumes an ingestion run without silently duplicating active content.

### Activation rule

- A document is invisible to search until it reaches `ready`.
- Activation occurs transactionally after extraction and embedding complete.
- If a new edition fails ingestion, the previously active edition remains searchable.

### Idempotency

- Source checksum prevents accidental duplicate uploads.
- Page, chunk, and asset writes are tied to an ingestion run.
- Reprocessing uses versioned configuration fingerprints.
- Re-running the same input and configuration should produce the same logical chunks and checksums.

## 8. Phase 1 — Data Extraction and Image Preservation

**Status: in progress (2026-07-16).**

### Current implementation checkpoint

- Selected `backend/data/Std_06/term1/6th_Science_Term_I.pdf` as the first local fixture; PDFs under
  `backend/data/` remain ignored and are never committed.
- Added the Docling standard digital-PDF adapter with OCR and vision disabled, lossless embedded
  Docling JSON, page/reading-order provenance, image extraction, intrinsic dimensions, canonical
  thumbnails, captions, and explicit accessibility metadata.
- Added deterministic page-contained, structure-aware chunks and persisted pages, chunks, assets,
  and run fingerprints in one extraction transaction. No embeddings are generated in this phase.
- Added a queue-claiming worker path with context-preserving blocking work, heartbeat continuity,
  sanitized failures, and temporary-file cleanup.
- Verified the selected book directly through the adapter: 108 pages, 433 chunks, and 293 images.
  CUDA-first execution on the local RTX 3050 completed the same extraction in about 140 seconds;
  the earlier CPU run took about 8.5 minutes.
- Switched the locked Torch runtime to CUDA 13.0 wheels while retaining `device=auto` GPU-first
  selection with CPU fallback. `compose.gpu.yaml` passes the host GPU to the worker on WSL2/NVIDIA
  development hosts.
- Added `backend/scripts/extract_book.py`, an offline GPU-first package builder for Colab or a
  workstation. It produces lossless Docling JSON, page/chunk/asset JSONL, preserved images, runtime
  metadata, source provenance, and SHA-256 checksums, with atomic no-overwrite publication and an
  optional deterministic ZIP archive. The package was validated against the selected book with the
  same 108-page, 433-chunk, 293-image result.

For the current deployment shape, GPU extraction is performed offline with that script and the
production container remains CPU-oriented. A future importer must verify the package manifest,
source SHA-256, file checksums, and extraction fingerprints before writing the immutable artifacts
and derived records to PostgreSQL/object storage. The API-upload-to-worker path remains available
for a later CPU extraction/retry workflow; it is not required for the GPU extraction handoff.

### Objective

Convert a digital textbook PDF into inspectable, page-linked text, chunks, and image assets without generating embeddings.

### Vertical slice

Start with one representative book and support the complete path:

`register book -> upload PDF -> queue ingestion -> extract -> inspect pages/chunks/assets`

Only after that slice works should ingestion be generalized to the remaining books.

### Work items

#### Upload and catalog

- Validate file type, size, and PDF readability.
- Compute source checksum before processing.
- Require standard, subject, title, language, and edition metadata.
- Persist the original PDF before creating an ingestion job.
- Reject or explicitly version duplicate checksums.

#### Docling extraction

- Configure the standard PDF pipeline without forced OCR.
- Detect whether a useful text layer exists.
- Preserve the lossless Docling JSON output.
- Capture page number, reading order, bounding boxes, item labels, and character spans where available.
- Record extraction warnings instead of silently dropping malformed elements.
- Fail fast with an unsupported-document reason for scan-only PDFs.

#### Page processing

- Build one normalized page record per PDF page.
- Preserve raw text exactly as extracted.
- Normalize line breaks, whitespace, Unicode, and repeated layout noise into a separate field.
- Identify recurring headers/footers carefully; preserve them in raw output even if excluded from retrieval text.
- Capture printed page labels where reliably available and allow later manual correction.

#### Image processing

- Export Docling picture assets in referenced-file mode.
- Store one canonical copy per asset checksum.
- Preserve page link, bounding box, caption, and Docling reference.
- Record intrinsic pixel dimensions for preserved raster assets so clients can reserve layout
  before loading their content.
- Generate one canonical aspect-preserving raster thumbnail during ingestion with the longest edge
  bounded by the deployment capability; record its dimensions and immutable artifact reference.
- Record explicit asset accessibility state: decorative, caption-derived alt text, manually
  remediated alt text, or unavailable. Do not send unavailable informative assets to the
  student-facing inline experience as if they were decorative.
- Do not generate page preview PNGs by default.
- Do not call a vision model.
- Define how an API will later authorize and serve asset files.

#### Chunking

- Chunk from the structured Docling document, not flattened PDF text alone.
- Prefer heading, paragraph, list, caption, and table boundaries.
- Keep chunks page-contained where possible.
- Preserve tables as coherent units or split them by meaningful row groups with repeated headers.
- Include book/chapter/section context in `embedding_text`, while keeping `display_text` faithful to the book.
- Target a conservative size below the embedding model's 512-token maximum; begin around 300–400 tokens and tune using real pages.
- Use tokenizer counts rather than character counts.
- Avoid arbitrary overlap; use small boundary overlap only when it improves continuity.
- Preserve sequence order for later neighbor expansion.

#### Worker behavior

- Claim jobs safely so only one worker processes a run.
- Update the stage after each durable milestone.
- Bound memory use and process one PDF at a time.
- Clean temporary files after success and retain useful diagnostics after failure.
- Make cancellation and retry behavior explicit.

### Inspection capability

Provide a development/admin way to inspect:

- Book and document metadata.
- Page text.
- Chunk boundaries and token counts.
- Extracted assets with their page and caption.
- Ingestion warnings and errors.

This can initially be an API or command-line inspection path; a frontend is not required.

### Tests

- Unit tests for normalization and deterministic chunking.
- Fixture-based extraction tests for paragraphs, headings, tables, and images.
- Checksum/idempotency tests.
- Failure tests for encrypted, corrupted, empty, and scan-only PDFs.
- Integration test covering upload through completed extraction.
- Manual visual comparison of selected PDF pages against stored page/chunk/asset provenance.

### Quality checks

- Every extracted page maps to the correct PDF page.
- Every chunk resolves to at least one page.
- No chunk exceeds the chosen tokenizer limit.
- Important headings and table headers are retained.
- Extracted images open successfully and map to the correct page.
- Re-ingestion with the same configuration produces stable chunk checksums.

### Exit gate

- At least three structurally different English textbooks ingest successfully.
- Page and asset provenance is manually verified on a representative sample.
- Scan-only and malformed files fail clearly.
- The extraction output is useful to inspect without an LLM.
- No major content class is silently lost.

## 9. Phase 2 — Local Embeddings and Semantic Retrieval

### Objective

Deliver a useful, completely local semantic-search endpoint backed by pgvector.

### Initial embedding decision

- Start with `BAAI/bge-small-en-v1.5`.
- Store 384-dimensional normalized vectors.
- Pin the model revision rather than relying on a floating remote revision.
- Cache the model in a controlled location.
- Prefer CPU inference initially for a simpler Docker setup; benchmark optional CUDA use separately.
- Use the same tokenizer and model configuration for document and query embeddings.

### Work items

#### Embedding pipeline

- Batch chunk embedding in the ingestion worker.
- Skip unchanged chunks using the content checksum and model revision.
- Persist model metadata with each embedding batch.
- Mark the document ready only after all active chunks have valid embeddings.
- Provide a controlled re-embedding operation for a changed model or preprocessing rule.

#### Retrieval query

- Implement the pgvector-backed retriever as an application adapter satisfying the
  `tnpsc_rag` retrieval protocol.
- Generate a normalized query embedding locally.
- Use cosine similarity consistently.
- Begin with exact pgvector search.
- Apply book, standard, subject, edition, and language filters in SQL.
- Return stable ordering for tied scores.
- Do not add HNSW until corpus size and measured latency justify it.

#### Search API

`POST /v1/search` should support:

- Query text.
- `top_k` with safe bounds.
- Optional standard filter.
- Optional subject filter.
- Optional book/document filters.
- Optional inclusion of neighboring chunk metadata, disabled by default.

Each result should include:

- Chunk ID and display text.
- Retrieval score with clear model-specific semantics.
- Book title, edition, standard, and subject.
- Printed page label and PDF page index.
- Chapter/section path.
- Associated captioned assets or asset references when relevant.
- No generated explanation.

#### Indexing

- Add ordinary indexes for document state and common metadata filters.
- Measure exact-search performance first.
- If required later, add HNSW with a recorded recall comparison against exact search.

### Retrieval evaluation set

Create a versioned benchmark containing:

- Direct factual questions.
- Questions that paraphrase the textbook wording.
- Chapter/section lookup queries.
- Questions whose answer is in a table or caption.
- Similar concepts appearing in multiple grades or books.
- Unanswerable/out-of-corpus questions.

For each answerable query, record one or more relevant chunk/page IDs rather than only a natural-language expected answer.

### Metrics

- Recall@1, Recall@5, and Recall@10.
- Mean reciprocal rank.
- Filter correctness.
- Page/citation correctness.
- Query-embedding latency.
- Database-search latency and total endpoint latency.
- Empty/irrelevant result behavior.

Initial targets should be agreed after the first benchmark is labeled. A practical starting gate is Recall@5 of at least 0.85 on the curated MVP set and p95 search latency under one second on the development laptop at expected corpus size.

### Tests

- Deterministic query embedding tests within numerical tolerance.
- Retrieval tests with known nearest neighbors.
- Metadata-filter isolation tests.
- Empty query and invalid `top_k` validation.
- Corpus activation tests ensuring incomplete documents never appear.
- API contract tests.
- Offline test proving search works without provider API keys or network access.

### Exit gate

- Semantic search returns relevant, cited chunks for the benchmark.
- Retrieval metrics meet the agreed threshold.
- Search works when all LLM provider keys are absent.
- Latency is acceptable with exact search.
- Known retrieval failures are documented before generation begins.

## 10. Phase 3 — Context Augmentation and Citation Assembly

### Objective

Transform raw search results into a compact, deterministic evidence package suitable for an LLM, without calling an LLM yet.

### Work items

- Finalize the initial `EvidencePack` contract in `tnpsc_rag` without adding provider behavior.
- Retrieve a larger candidate set than is ultimately sent to generation.
- Remove duplicate or highly overlapping chunks.
- Preserve ranking while limiting repeated evidence from the same page.
- Add preceding/following chunks only when needed for continuity.
- Distinguish semantic hits from neighbor-expanded context.
- Enforce a configurable context-token budget.
- Preserve chapter and section headings.
- Serialize tables without losing header meaning.
- Associate relevant captioned assets as metadata; do not send image pixels to a text-only model.
- Assign stable citation labels to evidence records.
- Record why each context item was included: semantic match, neighbor, or structural parent.
- Define behavior when no evidence meets the retrieval policy.

### Answer-mode policies

#### `textbook_only`

- Context contains only retrieved textbook evidence and its metadata.
- The future generator must be allowed to abstain.
- No system-supplied general facts are added.

#### `textbook_plus_general`

- The same textbook evidence is supplied first.
- The future generator is explicitly allowed to add general explanation.
- The output contract must distinguish sourced textbook claims from unsourced supplementary material.

### Inspection and debugging

Add an internal or development-only context preview that shows:

- Original query.
- Search parameters.
- Ranked hits.
- Neighbor expansions.
- Final token count.
- Citation mapping.
- Exclusion reasons.

### Tests

- Deterministic evidence-pack snapshots.
- Token-budget enforcement.
- Deduplication and neighbor-expansion tests.
- Citation-label stability.
- Table and caption preservation tests.
- No-evidence behavior.
- Tests ensuring inactive or filtered documents cannot enter the context indirectly.

### Exit gate

- A developer can inspect exactly what an LLM would receive.
- Context fits the configured budget.
- Every evidence item resolves to valid book/page provenance.
- Both answer modes have explicit, testable policies.
- No provider integration is required to test augmentation.

## 11. Phase 4 — PydanticAI v2 Answer Generation

### Objective

Generate explanations from the proven retrieval and augmentation pipeline while keeping provider behavior replaceable and auditable.

### Provider approach

- Implement PydanticAI as an application adapter satisfying the `tnpsc_rag` generation protocol.
- Keep prompts, evidence policies, and citation validation provider-neutral in `tnpsc_rag`.
- Evolve the preliminary `GenerationResult` into closed text/citation segment contracts before
  implementing the provider adapter; do not recover citation positions by parsing model prose.
- Use the stable PydanticAI v2 integration inside the API application boundary.
- Use typed Pydantic output models for answers, citations, abstention, and supplementary sections.
- Keep the agent minimal: no tools, graph, MCP, multi-agent workflow, or durable execution is required.
- Configure native Groq, OpenRouter, and Mistral providers through environment/settings.
- Use PydanticAI's `FallbackModel` as the only fallback layer.
- Prefer Groq free access as the initial primary when available.
- Use OpenRouter `:free` models as a fallback, not as a guaranteed dependency.
- Support a Mistral provider or Mistral-family model when free quota is available.
- Do not assume any named free model will remain available.
- Pin the PydanticAI major version and provider SDK versions.
- Consider a separate LiteLLM proxy later only if multiple applications need shared keys, quotas, routing, or accounting.

### Answer API

`POST /v1/answers` should accept:

- Query text.
- `mode`: `textbook_only` or `textbook_plus_general`.
- The same metadata filters as semantic search.
- Bounded retrieval and response-length controls.
- `application/json` and opt-in `text/event-stream` response representations for the same request.

The answer response should include:

- Generated explanation as ordered text/citation blocks rather than client-parsed citation syntax.
- Answer mode actually applied.
- Structured citations.
- Exact evidence chunks used.
- An abstention or insufficient-evidence indicator.
- Supplementary-material marker when applicable.
- Request ID for diagnostics.

Persist the public answer-run state needed for `GET /v1/answers/{answer_id}` so an interrupted SSE
client can recover without replaying generation. Retain running/final state, the validated
structured result or sanitized problem, timestamps, and request ID for at least the capability
endpoint's advertised retention window.

The SSE representation emits progress and explicitly provisional text deltas, may reset that
preview when fallback or validation restarts generation, and terminates with the same validated
structured answer as the JSON representation. Only the terminal answer is canonical.

Provider/model details may remain internal but must be recorded in `answer_runs`.

### Strict grounding behavior

- In `textbook_only`, every material factual claim should have a citation.
- Citation IDs must be validated against the supplied evidence pack.
- Unknown citation IDs cause validation failure or regeneration, never silent acceptance.
- The model must state that the evidence is insufficient when it cannot answer from the context.
- Prompt instructions alone are not considered enforcement.
- Add a lightweight post-generation validator for citation existence, source membership, and response structure.

### Supplemented behavior

- Textbook-supported explanation remains primary.
- General model knowledge is clearly labeled as supplementary.
- General material must not receive textbook citations.
- The response must not imply that supplementary claims occur in the cited page.

### Reliability

- Use bounded timeouts.
- Retry only transient failures.
- Honor `Retry-After` when available.
- Fall back on rate-limit, timeout, and service-unavailable errors.
- Cap total attempts and total request duration.
- Return a clear capacity error when all free providers are unavailable.
- Never degrade or change the requested answer mode during fallback.
- If fallback or validation retry occurs after provisional SSE text has been emitted, send an
  explicit reset before streaming replacement preview text.
- Keep `/v1/search` healthy during all generation-provider failures.

### Prompt and model versioning

- Version system prompts and response contracts.
- Record the prompt version, provider, model, and evidence IDs for each answer.
- Evaluate a model before adding it to the fallback pool.
- Do not rely on provider-specific structured-output features unless the selected fallback models all support them; retain a validated portable response path.

### PydanticAI testing and observability

- Set `ALLOW_MODEL_REQUESTS=False` in the default test environment.
- Use `TestModel` for schema and agent-flow tests.
- Use `FunctionModel` for deterministic domain-specific model behavior and failure cases.
- Use dependency/model overrides rather than patching network clients deep inside application code.
- Instrument agent runs with OpenTelemetry.
- Use telemetry format version 5 or the current non-deprecated default.
- Set `include_content=False` by default so prompts, evidence, completions, and binary assets are not exported.
- Record provider/model, token counts, duration, retries, and fallback decisions without recording secrets.
- Introduce Pydantic Evals for versioned answer-quality datasets after deterministic tests are stable.

### Privacy and security

- Free hosted generation sends the query and selected textbook excerpts to a third party.
- Document this behavior clearly.
- Never send the complete textbook when a small evidence pack is sufficient.
- Redact keys from errors and logs.
- Restrict provider keys to the backend.

### Tests

- PydanticAI `TestModel` and `FunctionModel` tests for both answer modes.
- Structured answer-block tests proving every citation node resolves to returned evidence without
  frontend string parsing.
- SSE tests for event order, provisional reset, keepalive behavior, disconnect cancellation, and
  exactly one terminal completion or failure event.
- Citation validation tests, including fabricated IDs.
- Abstention tests for missing evidence.
- Supplement-labeling tests.
- Timeout, 429, provider outage, and fallback tests.
- Test proving provider failure does not break semantic search.
- Opt-in live smoke tests that do not run in the normal test suite.

### Evaluation

- Answer correctness against textbook evidence.
- Citation precision and citation completeness.
- Groundedness/faithfulness review.
- Abstention accuracy.
- Leakage of general knowledge into `textbook_only`.
- Clear labeling of supplementation.
- Latency and provider failure rate.

### Exit gate

- Both modes meet their documented behavior on the benchmark.
- Fabricated citations are rejected.
- Strict mode abstains when evidence is insufficient.
- Supplemented claims are visually and structurally distinct.
- Provider exhaustion returns a controlled error while search remains operational.
- Normal CI cannot make a real model request.

## 14. Testing Strategy by Layer

### Static quality gates

- Ruff checks formatting, imports, common defects, and selected security rules.
- `ty` is the primary fast local type checker and a blocking CI check.
- Pyrefly runs with the strict preset as an independent blocking CI check.
- Both type checkers cover `src` and tests from the beginning of the project.
- Type-checker versions are pinned; upgrades happen in dedicated changes so new diagnostics are reviewable.
- Suppressions are narrow, rule-specific, and include a reason. A global baseline of ignored errors is not accepted for this new codebase.

### Unit tests

- Use pytest with AnyIO support for asynchronous application code.
- Use pytest-cov/coverage.py with branch coverage to reveal untested paths; do not optimize for a vanity 100% target.
- Text normalization.
- Chunking and token limits.
- State transitions.
- Storage paths and checksums.
- Evidence selection and citation mapping.
- Prompt/output validation.
- Provider error classification and fallback decisions.
- Pure business logic runs without Docker, PostgreSQL, Docling, or network access where feasible.

### Property-based tests

- Use Hypothesis for invariant-driven tests.
- Whitespace and Unicode normalization invariants.
- Chunk size, order, and provenance invariants.
- State-machine transitions and idempotent retries.
- Bounded request values such as `top_k` and context limits.
- Citation IDs can never escape the supplied evidence set.

### Integration tests

- PostgreSQL migrations and repositories against real PostgreSQL with pgvector.
- Docling extraction of small synthetic or redistributable fixtures containing headings, tables, and images.
- pgvector retrieval and filters.
- Worker job claiming and retry.
- Artifact persistence.
- FastAPI request/response contracts through an in-process HTTP client.
- PydanticAI integration through `TestModel` and `FunctionModel`.

### End-to-end tests

- PDF upload through extracted document.
- PDF upload through searchable document.
- Search with page-correct citations.
- Strict answer with valid evidence.
- Strict abstention without evidence.
- Supplemented answer with clear labeling.
- Provider outage while local search remains available.
- Worker interruption, lease expiry, retry, and recovery.
- Duplicate upload and safe re-ingestion.

The primary end-to-end test is deterministic and offline:

`PDF upload -> extraction -> chunking -> embedding -> search -> evidence pack -> FunctionModel answer -> citation validation`

### Retrieval evaluation

- Maintain a versioned dataset mapping each query to relevant chunk/page IDs.
- Report Recall@1, Recall@5, Recall@10, mean reciprocal rank, filter correctness, and latency.
- Compare approximate indexes against exact search before enabling them.
- Fail the retrieval regression gate when an accepted baseline degrades beyond an agreed tolerance.

### Generation evaluation

- Keep evaluation datasets separate from ordinary unit-test fixtures.
- Evaluate correctness, citation precision/completeness, groundedness, abstention, supplementary-label clarity, and latency.
- Use deterministic evaluators where possible; LLM-as-judge evaluation is supplementary and never the only release gate.
- Version the prompt, model/fallback configuration, evidence policy, dataset, and evaluator together in reports.
- Evaluate a provider/model before adding it to the production fallback chain.

### Network policy

- Normal unit, integration, and end-to-end tests do not call hosted models.
- PydanticAI model requests are globally disabled unless a test explicitly opts in.
- Live provider smoke tests use a separate marker, explicit environment opt-in, and strict request/token caps.
- Provider quota exhaustion never makes the normal CI suite flaky.

### Manual QA

- Visual comparison of PDF pages and extracted content.
- Inspection of tables and image captions.
- TNPSC-style question review.
- Citation navigation from answer to correct page and asset.
- Restore-drill verification and operational runbook rehearsal before production.

## 15. Risk Register

| Risk | Effect | Mitigation |
|---|---|---|
| PDF reading order is incorrect | Poor chunks and retrieval | Inspect Docling structure, retain raw JSON, add fixture regressions |
| Printed page differs from PDF page | Misleading citations | Store both fields and allow correction |
| Important content exists only in images | Text RAG cannot answer it | Preserve assets now; defer multimodal retrieval explicitly |
| Chunking splits definitions or tables | Reduced retrieval quality | Structure-aware chunking and retrieval benchmark cases |
| Embedding scores appear high for unrelated text | Bad threshold assumptions | Evaluate relative rank; calibrate any threshold on the corpus |
| Free LLM model disappears | Answer endpoint outage | Configured PydanticAI `FallbackModel` chain and controlled capacity error |
| Free quota is exhausted | Generation unavailable | Keep search local; cache only safe identical outputs; expose retry information |
| Provider changes output format | Citation parsing failures | Portable response contract and backend validation |
| LLM fabricates citations | False trust | Server-side citation membership validation and abstention policy |
| Disk usage grows unexpectedly | Failed local development | No page renders by default, checksum deduplication, cleanup and monitoring |
| Python/ML dependency mismatch | Build failure | Verify runtime in Phase 0 and pin reproducible dependency versions |
| Re-ingestion changes chunk IDs | Broken audit trails | Stable checksums, versioned runs, immutable historical document versions |
| Malicious or pathological PDF consumes resources | Worker outage or denial of service | Validate uploads and isolate parsing with CPU, memory, page-count, file-size, and timeout limits |
| Public admin endpoint is abused | Corpus corruption or deletion | Require authentication and explicit authorization for all mutation/admin operations |
| Telemetry leaks prompts or textbook content | Privacy or licensing exposure | Metadata-only telemetry by default and `include_content=False` for PydanticAI |
| Backup exists but cannot be restored | Irrecoverable data loss | Scheduled restore drills and documented RPO/RTO |
| Two type checkers disagree | Developer friction | Pin versions, use narrow documented suppressions, and validate behavior with runtime tests |
| Model/prompt change silently lowers quality | Retrieval or answer regression | Versioned eval gate before rollout and rollback to the previous configuration |

## 16. Production Service Checklist

The local MVP is not automatically production-ready. The following controls become mandatory before the service is exposed to untrusted users or relied upon as a persistent shared service.

### 16.1 Hosting and network boundary

- Treat the laptop Docker Compose setup as development infrastructure, not a production topology.
- Place the public API behind TLS termination with correctly configured trusted-proxy and forwarded-header handling.
- Keep PostgreSQL, artifact storage, worker controls, metrics, traces, and debug endpoints off the public network.
- Restrict administrative routes by both authentication and network policy where practical.
- Use durable production storage or managed PostgreSQL/object storage with explicit persistence and backup guarantees.
- Choose redundancy and high availability from the agreed SLO/RPO/RTO rather than adding distributed infrastructure by default.
- Document every accepted single point of failure in the first production deployment.

### 16.2 Identity and authorization

- Decide whether search is public, authenticated, or both.
- Require authentication for uploads, metadata edits, activation, deletion, reprocessing, re-embedding, and operational endpoints.
- Separate reader and administrator permissions even if the first production deployment has only one administrator.
- Enforce authorization in the backend; hiding controls in the frontend is not authorization.
- Use short-lived or rotatable credentials and document emergency revocation.
- Keep health endpoints minimal and protect debug, metrics, trace, and context-preview endpoints.

### 16.3 Abuse prevention and resource governance

- Apply per-client rate limits and global concurrency limits.
- Bound request body size, PDF size, page count, query length, `top_k`, filter breadth, context tokens, response tokens, processing time, and retry count.
- Add backpressure so uploads cannot create an unbounded worker queue.
- Reserve capacity for health checks and ordinary search while ingestion is busy.
- Return standard `413`, `429`, timeout, and capacity errors with safe retry guidance.
- Load-test search, ingestion, and mixed workloads at expected and failure-level concurrency.
- Define a degradation policy: search stays available when generation providers fail; uploads may pause before search is impacted.

### 16.4 Secure document processing

- Treat every uploaded PDF as untrusted input.
- Validate the file signature and parser result rather than trusting the filename or MIME header.
- Generate storage names server-side and store uploads outside a directly executable/web-served path.
- Reject encrypted, corrupted, unexpectedly huge, scan-only, or unsupported documents with stable error codes.
- Run Docling in an unprivileged worker/container with constrained CPU, memory, temporary storage, and wall-clock time.
- Prevent uploaded documents from selecting local paths, arbitrary output paths, or unexpected remote URLs.
- Patch PDF, image, ML, and archive-processing dependencies promptly.
- Consider malware scanning or content disarm/reconstruction if document upload is opened beyond trusted administrators.

### 16.5 Secrets and supply-chain security

- Store provider and database credentials in the deployment secret mechanism, not images, Compose files, source control, or logs.
- Support key rotation without rebuilding application images.
- Lock Python dependencies and pin container base images intentionally.
- Run dependency, container, secret, and license scans in CI.
- Generate an SBOM for production images.
- Run containers as non-root, drop unnecessary Linux capabilities, and prefer read-only filesystems with explicit writable mounts.
- Keep development/debug settings disabled in production.

### 16.6 Data integrity, privacy, and legal review

- Confirm permission to ingest, retain, excerpt, and display textbook pages and images.
- Document which query/evidence content is sent to each hosted LLM provider and review provider retention/training terms.
- Default traces and logs to content-free metadata.
- Define retention and deletion rules for PDFs, extracted assets, failed-ingestion artifacts, queries, answers, audit records, backups, and telemetry.
- Make deletion cover database records, artifact storage, caches, and future backups according to the documented retention policy.
- Encrypt traffic in transit and production data/backups at rest.
- Record document source, checksum, edition, ingestion configuration, and activation history for auditability.

### 16.7 Availability and graceful degradation

- Define service-level objectives separately for local search, ingestion, and hosted answer generation.
- Treat free hosted generation as best-effort unless a provider SLA is purchased later.
- Use bounded timeouts, circuit breaking, fallback limits, and load shedding.
- Make worker leases recoverable after process or host failure.
- Add a dead-letter/manual-remediation path for poison documents.
- Test API restart, worker restart, database restart, provider outage, storage-full, and partial-ingestion scenarios.
- Ensure shutdown drains or safely abandons in-flight work without corrupting activation state.

### 16.8 Backup and disaster recovery

- Back up PostgreSQL and artifact storage as one documented recovery set.
- Define recovery point objective and recovery time objective.
- Encrypt backups and keep at least one copy outside the primary host/storage failure domain.
- Automate backup success monitoring.
- Perform scheduled restore drills and verify checksums, migrations, active document versions, assets, and search behavior after recovery.
- Add PostgreSQL WAL archiving and point-in-time recovery when the required RPO justifies it.
- Do not classify a backup strategy as complete until restore time has been measured.

### 16.9 Deployment and change management

- Separate development, test/staging, and production settings and credentials.
- Build one immutable image and promote it rather than rebuilding differently per environment.
- Use backward-compatible expand/migrate/contract database changes where rolling deployment is required.
- Define application and migration rollback procedures.
- Gate dependency, embedding-model, chunker, prompt, provider, and fallback changes with their relevant regression suites.
- Store the last-known-good model/prompt/retrieval configuration for rapid rollback.
- Use a canary or restricted rollout for changes that can affect answer quality.

### 16.10 Observability, SLOs, and incident response

- Define service indicators for availability, search latency, ingestion success/time, queue age, generation success/latency, citation validation, and disk/database capacity.
- Create alerts from SLOs and capacity thresholds rather than every individual exception.
- Maintain dashboards or saved queries that link symptoms to trace and run IDs.
- Set log, trace, and metric retention and sampling policies.
- Write runbooks for provider exhaustion, slow/failed ingestion, stuck jobs, low disk, high database connections, backup failure, and bad deployment.
- Assign ownership for responding to alerts before calling the service production.
- Review telemetry cardinality and content exposure before each new instrumented feature.

### 16.11 API and client compatibility

- Publish an explicit API versioning and deprecation policy.
- Preserve stable error codes even when human-readable messages change.
- Add idempotency behavior for mutation requests.
- Define pagination cursors/order and maximum page sizes.
- Support opt-in exact collection counts without making count queries the infinite-scroll default.
- Use ETags or equivalent cache validators for immutable assets where useful.
- Document timeout, retry, and rate-limit behavior for clients.
- Treat `openapi.v1.yaml` as the machine contract for client generation and fail CI when its
  implemented subset drifts from FastAPI's generated schema or normative examples.
- Test every documented JSON example and known SSE payload against the checked-in schemas.
- Never expose internal filesystem paths, provider errors, SQL details, or stack traces.

### 16.12 Production security and quality gates

- Perform an API threat model covering authorization, resource exhaustion, unsafe file processing, secrets, provider dependencies, and data exposure.
- Review the service against the OWASP API Security Top 10 before public exposure.
- Run automated vulnerability scans and remediate release-blocking findings.
- Test authorization failures, rate limiting, oversized uploads, parser timeouts, malformed PDFs, log sanitization, and secret redaction.
- Require successful static checks, deterministic tests, database tests, extraction fixtures, retrieval evaluation, generation evaluation, container scans, and backup restore evidence for a production release.

### 16.13 Production exit gate

- Administrative mutations require tested authentication and authorization.
- Untrusted uploads are isolated and resource-bounded.
- Search and mixed-workload load tests meet the agreed SLOs.
- Database and artifact backups have passed a restore drill.
- Alerts and runbooks cover the critical failure modes.
- Content retention, provider data handling, and textbook rights are documented.
- Release and rollback paths are rehearsed.
- A provider outage degrades only answer generation, not local search or corpus integrity.
